# 002 — План

## Решение

Конвейер SRS §5.1 целиком. Браузер уменьшает фото до 1600 px и конвертирует в JPEG
(SRS §5.2), отправляет один `multipart/form-data` с `Idempotency-Key`. HTTP-запрос
не тратит ни такта на изображения (SRS §5.3): лимиты на потоке, magic bytes, **геозабор
до единого байта в S3**, PUT сырых байт в `incoming/`, одна транзакция
(`report` + `report_photo` в `PENDING` + история + сигналы антиабуза) и `201`
с `photosPending: true`. Перекодирование, вырезание EXIF, превью и `sha256` делает
photo-воркер — `setInterval` в том же процессе, одна задача за раз, захват через
`FOR UPDATE SKIP LOCKED` (SRS §5.4, ADR-0007).

Граница между двумя половинами конвейера — единственное, что отделяет систему
от падения под всплеском (SRS §1.6): всё, что стоит процессорного времени, происходит
после ответа клиенту.

Геометрия появляется ровно в одной таблице — `district` (ADR-0003). У заявки — обычные
`latitude`/`longitude`, поэтому `report` мигрирует и читается штатным Prisma Client.

## Контракт (`packages/shared-types`)

По ADR-0006 — один раз, обе стороны импортируют. Появляются:

- `CreateReportRequest` — поля из SRS §4.2 (без файлов: они идут частями multipart).
- `CreateReportResponse` — `number`, `displayNumber`, `trackingToken`, `trackingPath`,
  `districtCode`, `status`, `photosPending`, `createdAt` (SRS §4.2).
- `DistrictDto` — `code`, `nameUz`, `nameRu`, `bbox` (SRS §4.6).
- `CategoryDto` — `{ code, nameUz, nameRu }` **без union кодов**: список категорий —
  данные, а не тип (SRS §2.5), исчерпывающего union на этапе компиляции не существует.
- Типы результатов двух `$queryRaw` — район по точке и кандидаты в дубли (SRS §2.14).
- Новые `ErrorCode`: `OUTSIDE_TASHKENT`, `PHOTOS_REQUIRED`, `IDEMPOTENCY_CONFLICT`,
  `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `RATE_LIMITED`, `STORAGE_UNAVAILABLE`
  (SRS §4.2). Каждый добавленный код обязан получить строку в обеих локалях, иначе
  `pnpm typecheck` красный (SRS §8.1).

`displayNumber` считает сервер: формат `RR-` — часть контракта, и его дублирование
в двух локалях фронта разъедется раньше, чем понадобится (SRS §4.2).

## Схема БД

Таблицы по SRS §2.2–§2.6, §2.9, §2.13. Разбиты на четыре миграции, чтобы каждая
читалась на ревью целиком.

| Миграция | Содержимое | Раздел SRS |
| --- | --- | --- |
| `0002` | `district` (`geography(MultiPolygon,4326)` + GiST), `category`, сид обеих | §2.5, §2.6 |
| `0003` | `report`, `report_public_number_seq`, индексы, CHECK-инварианты | §2.1, §2.2 |
| `0004` | `report_photo`, `abuse_signal`, `form_open_counter` | §2.4, §2.9, §2.13 |
| `0005` | `report_status_history` | §2.7 |

**Что именно PostGIS.** Единственное поле `Unsupported` во всей схеме — `district.geom`
(ADR-0003). Ручной правки сгенерированного SQL требуют два объекта: `CREATE EXTENSION`
(уже в 001) и `CREATE INDEX ... USING GIST`. Появление второго `Unsupported` — повод
пересмотреть ADR-0003, а не расширить исключение молча.

`Polygon` приводится к `MultiPolygon` через `ST_Multi` при сиде, иначе
Мирзо-Улугбекский с эксклавом требовал бы отдельной обработки в каждом запросе
(SRS §2.6).

**Номер заявки** — `DEFAULT nextval('report_public_number_seq')`, не `COUNT(*) + 1`
(SRS §2.1). Пропуски номеров при откате транзакции — не дефект: номер обязан быть
уникальным, а не плотным.

**Обратная совместимость.** База пустая, накат тривиален. Начиная с этого среза
каждая миграция прогоняется на копии дампа перед мержем (SRS §13).

**Инвариант BR-006** одним `CHECK` не выражается и здесь не проверяется: переход
в `DONE` появляется только в 004 (SRS §2.2).

## Эндпоинты

| Метод | Путь | Тело / параметры | Ответ | Ошибки |
| --- | --- | --- | --- | --- |
| `POST` | `/api/reports` | `multipart/form-data` по SRS §4.2 + обязательный `Idempotency-Key` | `201 CreateReportResponse`; повтор с тем же ключом → `200` с тем же телом | `400 VALIDATION_FAILED`, `400 OUTSIDE_TASHKENT`, `400 PHOTOS_REQUIRED`, `409 IDEMPOTENCY_CONFLICT`, `413`, `415`, `429`, `503 STORAGE_UNAVAILABLE` |
| `GET` | `/api/districts` | — | 12 объектов с bbox, `Cache-Control: public, max-age=86400` | — |
| `GET` | `/api/categories` | — | активные категории, тот же кэш | — |
| `POST` | `/api/form-opens` | пустое | `204` | `429` |

Публичных эндпоинтов, меняющих данные без проверки, срез не добавляет: `POST
/api/reports` — единственный вход, и он ограничен геозабором, лимитами SRS §9.5
и семафором приёма.

**Порядок проверок в `POST /api/reports`** (SRS §5.3) — жёсткий, менять нельзя:
лимиты на потоке → magic bytes → **геозабор** → PUT сырых байт → транзакция → ответ.
Геозабор раньше файлов означает, что заявка вне города не стоит нам ни одного объекта
в S3.

**Семафор приёма — 8 одновременных запросов** ⚡ (SRS §4.2, §5.7). Порог выведен
из памяти, а не из процессора: 8 × 8 МБ = 64 МБ верхняя граница. Девятый запрос ждёт
до 20 с, дальше `429` с `Retry-After`. Это единственный жёсткий отказ на пути подачи.

## Telegram

В этом срезе не затрагивается. Строка `telegram_outbox` при создании заявки
**не появляется** (SRS §1.3 п.5): карточка ставится в очередь после обработки
последнего `BEFORE`-фото, и эта постановка добавляется в 004 отдельной задачей.
До неё photo-воркер доводит фото до `READY` и на этом останавливается.

## Frontend

**Маршрут** `/$locale/new` (SRS §7.1).

**Состояния экрана:** пустая форма, форма с восстановленным черновиком, отправка,
ошибка сети с кнопкой «повторить», экран подтверждения, экран подтверждения
с ожиданием превью.

**Сжатие на устройстве** (SRS §5.2): `createImageBitmap(file, { imageOrientation:
'from-image' })` → `OffscreenCanvas` → `convertToBlob({ type: 'image/jpeg',
quality: 0.82 })`. Поворот применяется к пикселям, поэтому после вырезания EXIF
на сервере фото не переворачивается. HEIC вне iOS даёт отказ промиса — показываем
понятную ошибку; библиотеку-конвертер не подключаем: ~1,5 МБ wasm при бюджете
страницы 700 КБ.

**Карта** (SRS §7.4, ADR-0004): Яндекс JS API v3 грузится динамическим `import()`
только на маршрутах с картой. Виджет выбора точки и тайлы — единственное, что берётся
у Яндекса; геокодер не вызывается ни при каких условиях. Доступная альтернатива
перетаскиванию — кнопка «моё местоположение» и два числовых поля, связанных с тем же
состоянием, что и пин.

**Черновик** (SRS §7.6): поля, координаты, **уже сжатые** фото как Blob и
`Idempotency-Key` кладутся в IndexedDB — в `localStorage` бинарные данные
не помещаются. Живёт 24 часа. «Повторить» переиспользует тот же ключ.

**TanStack Query** (SRS §7.5): `['districts']` и `['categories']` со `staleTime:
Infinity`; свежесозданная заявка с `photosPending: true` перезапрашивается каждые
3 секунды не более 10 раз — это единственное исключение из правила «не опрашивать».
Блокировать экран ожиданием превью нельзя: житель не должен стоять у ямы, глядя
на спиннер.

## Риски

| Риск | Что делаем |
| --- | --- |
| ⚡ **Всплеск 1000 заявок/час** (SRS §1.6) | Ресайз вынесен из HTTP-запроса в очередь (ADR-0007); приём ограничен семафором, а не отказом; переполнение очереди заявку не отклоняет — очередь это строки в таблице |
| ⚡ Задержка S3 выше ожидаемой (SRS §16 п.19) | Пропускная способность падает до ~1,2 фото/с; ответ — второй воркер, это одна константа. Число воркеров вынести в конфигурацию с первого коммита |
| ⚡ Память под всплеском | `sharp.concurrency(1)`, `VIPS_CONCURRENCY=1`, `sharp.cache({memory:32})`, одна задача за раз, `limitInputPixels: 50_000_000` (SRS §5.7) |
| Диск как буфер | Локального spool-каталога нет вовсе: сырые байты идут прямо в S3, lifecycle-правило бакета чистит `incoming/` (SRS §5.5, §5.7) |
| Осиротевшие объекты в бакете | Принято: ~200 КБ и редкий случай, сборщик мусора в MVP не пишется; порог для его появления — >1% объектов без строк (SRS §5.5) |
| Полиглоты и бомбы | Всё перекодируется, исходные байты не сохраняются; SVG не принимается ни на каком этапе (SRS §9.6) |
| Спуфинг координат | Сервер всегда пересчитывает район сам; значение из клиента не принимается (SRS §9.7) |
| CGNAT ломает лимиты по IP | Жёсткий порог только 60/час — это DoS-барьер, а не антиспам; мягкий 10/час ставит флаг (SRS §9.5, PRD §10.4) |
| **VPS 2 ГБ / GCE 1 ГБ** | Семафор приёма на dev — 2, а не 8 (SRS §12.2); photo-воркер один в обеих средах; всплеск на dev не воспроизводится и не должен |
| Prisma не читает `geography` | Два `$queryRaw` с ручной типизацией, типы объявлены в `shared-types` и покрыты интеграционными тестами (ADR-0003, SRS §2.14) |

## Проверка

1. Форма с телефона: 3 фото, пин, категория → `201`, номер `RR-…`, ссылка на экране.
2. `POST /api/reports` с координатами Самарканда → `400 OUTSIDE_TASHKENT`;
   `SELECT count(*) FROM report` не изменился; в бакете нет новых объектов.
3. Точка `69.454308, 41.413567` → `districtCode = mirzo-ulugbek`.
4. Остановить photo-воркер → отправить заявку → `201`, `photosPending: true`,
   строка в БД есть. Запустить воркер → фото доходят до `READY`.
5. `exiftool` по итоговому объекту в S3 → ни одного тега, включая GPS.
6. Три `POST` с одним `Idempotency-Key` → одна строка в `report`, второй и третий
   ответы `200` с тем же телом.
7. 100 параллельных `POST` → `SELECT count(DISTINCT public_number)` = 100.
8. Заполнить honeypot → заявка создана, в `abuse_signal` строка `HONEYPOT`.
9. 61 запрос за час с одного адреса → `429` с `Retry-After`.
10. Отключить сеть в DevTools на отправке → черновик восстановился со сжатыми фото;
    «повторить» после включения сети создало одну заявку.
11. Пройти форму целиком с клавиатуры, включая выбор координат.
12. `pnpm lint && pnpm typecheck && pnpm test` зелёные; интеграционные тесты на
    Testcontainers проходят (SRS §11.3).
