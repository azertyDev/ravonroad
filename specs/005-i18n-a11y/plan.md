# 005 — План

## Решение

Локализация устроена по SRS §8.2: сервер отдаёт **коды**, клиент держит словарь
`code → строка` на каждую локаль. Из этого правила ровно одно осознанное исключение —
категории: их переводы живут в БД (SRS §2.5), иначе новая строка таблицы требовала бы
передеплоя фронта, то есть ровно того, чего решение с категориями-данными избегает.

Полнота словарей проверяется двумя механизмами, ни один из которых не «глазами»:
`pnpm typecheck` ломается на новом `ErrorCode` без строки локали (ADR-0006, SRS §8.1),
а unit-тест сравнивает множества ключей `uz` и `ru` (SRS §11.2).

Доступность закрывается по списку PRD §8.2 — восемь пунктов, каждый со своей задачей.
Проверяемых автоматически из них два (контраст палитры, размер целей); остальные
проверяются руками по чек-листу, потому что автоматизация здесь дороже самого требования
(SRS §11.5).

## Затрагиваемые модули

| Модуль | Что меняется |
| --- | --- |
| `apps/web/src/shared/i18n` | Полные словари `uz.json` и `ru.json`, тест равенства ключей |
| `apps/web/src/entities/report` | Локализация статусов, причин, признака отмены |
| `apps/web/src/entities/district` | Названия районов из глоссария |
| `apps/web/src/entities/category` | Категории из БД, обе локали |
| `apps/web/src/shared/ui/form` | Связь ошибок с полями, подписи |
| `apps/web/src/shared/ui/status` | Формы статусов, подписи |
| `apps/web/src/index.css` | Токены контраста, размеры целей |
| `apps/web/src/features/report-form`, `report-filters`, `report-map` | Клавиатурная проходимость |

## Контракт

Изменений в `packages/shared-types` срез не вносит: все коды уже объявлены в 001–004.
Появляется зависимость обратного направления — **тип словаря выводится из union-ов
контракта**, поэтому пропуск строки для нового кода ломает сборку, а не остаётся
замечанием на ревью (SRS §8.1).

Названия районов берутся из свойств `data/geo/tashkent-districts.geojson` и таблицы
глоссария, а не переписываются вручную. Латиница использует `ʻ` (U+02BB) в `oʻ`/`gʻ`
и `ʼ` (U+02BC) для твёрдого знака — как в датасете.

## Схема БД

Новых таблиц и колонок нет. Проверяется полнота **данных**: `category.name_uz`
и `name_ru` заполнены у всех активных строк, `district.name_uz`/`name_ru` совпадают
с глоссарием. Проверка — интеграционный тест на сид, а не ручная сверка.

## Эндпоинты

Не меняются. `GET /api/categories` уже отдаёт `nameUz`/`nameRu` (002, SRS §2.5);
`GET /api/districts` — названия районов. Локаль ответа роли не играет: сервер отдаёт
коды (SRS §4).

## Telegram

Не затрагивается. Тексты бота остаются на одном языке: группа волонтёров одна,
и PRD двух локалей для неё не требует. Причины отказа, которые модератор выбирает
кнопкой, хранятся кодами — и именно поэтому житель читает их на своём языке
на `/z/<token>`, а не в формулировке модератора.

## Frontend

**Словари** — по одному JSON на локаль, ключи плоские и совпадают по множеству.
Разделены на секции по смыслу: интерфейс, статусы, причины `REJECTED`, причины
`OUT_OF_SCOPE`, районы, ошибки.

**Свободный текст модератора** (причина «другое») не переводится и показывается
как введён — рядом стоит поясняющая строка, сама по себе переведённая (SRS §8.2).

**Контраст** проверяется unit-тестом по палитре токенов: пары «текст на фоне»
объявлены явно, тест считает отношение и падает ниже 4,5:1 (3:1 для крупного).
Это дешевле, чем прогонять axe по каждому экрану, и ловит реальную причину нарушений —
правку токена.

**Размер целей** — минимум 24×24 CSS-пикселя (WCAG 2.2 Target Size Minimum). Проверка:
общий класс для интерактивных элементов и тест, что ни один компонент его не обходит.

**Клавиатура** — сквозной проход по чек-листу: форма (включая выбор координат
без перетаскивания, US-007), фильтры, карта, переключатель языка, кнопка удаления
контактов. Порядок фокуса совпадает с визуальным, фокус видим на каждом шаге.

**Статусы** различаются формой и подписью, а не только цветом (PRD §8.2). Формы взяты
из токенов 001, здесь добавляются подписи и проверка в монохроме.

**Список как альтернатива карте** уже существует (003): PRD §8.2 требует, чтобы карта
не была единственным способом увидеть заявки. Здесь проверяется, что список даёт
**тот же** набор данных и **те же** фильтры.

**Неподдерживаемый браузер** — сообщение вместо молча сломанной страницы (PRD §8.5).
Определение по наличию используемых возможностей (`createImageBitmap`,
`OffscreenCanvas`), а не по строке user-agent.

## Риски

| Риск | Что делаем |
| --- | --- |
| Перевод «технически полный», но нечитаемый | Вычитка носителем языка вынесена в «Требует решения»; глоссарий фиксирует термины, но не тексты |
| Словарь расходится с глоссарием | Расхождение объявлено ошибкой ревью (глоссарий); термины берутся из таблиц, а не сочиняются |
| Апострофы `ʻ`/`ʼ` заменяются на `'` при копировании | Тест сравнивает названия районов со свойствами GeoJSON посимвольно |
| Категории переводятся дважды — в БД и в словаре | Явно запрещено: категории только из БД (SRS §2.5). Тест: в словарях нет ключей категорий |
| Проверка доступности превращается в бесконечную | Ограничена восемью пунктами PRD §8.2; всё сверх — вне рамок среза |
| Проверка на iPhone откладывается | Вынесена отдельной задачей с результатом в SRS §16 п.3; без неё срез не закрыт |
| **VPS 2 ГБ / GCE 1 ГБ** | Срез не добавляет ни процессов, ни контейнеров, ни зависимостей. Единственное влияние на ресурсы — рост словарей: они входят в бюджет бандла 700 КБ и проверяются гейтом из 001 |

## Проверка

1. `pnpm test` → тест равенства множеств ключей `uz`/`ru` зелёный; тест полноты
   словаря `ErrorCode` зелёный.
2. Обойти все экраны на `/uz` → ни одного русского или английского слова, включая
   статусы, категории, причины и районы.
3. Открыть `/uz/z/<token>` заявки в `REJECTED` с причиной «другое» → код причины
   переведён, текст модератора показан как введён с поясняющей строкой.
4. `INSERT` новой категории в БД → она появилась в форме на обоих языках без пересборки.
5. Сравнить названия районов в словаре со свойствами `tashkent-districts.geojson` —
   посимвольно, включая U+02BB и U+02BC.
6. Пройти форму, фильтры и карту только с клавиатуры → всё достижимо, фокус виден,
   порядок совпадает с визуальным.
7. Скринридер на форме → каждая ошибка зачитывается вместе с полем.
8. `pnpm test` → проверка контраста по палитре зелёная; проверка размеров целей зелёная.
9. Включить монохромный режим ОС → семь статусов различимы.
10. Открыть сайт на реальном iPhone, отправить заявку с фото из галереи → заявка
    создана; результат по HEIC записан в SRS §16 п.3.
11. Открыть в браузере без `OffscreenCanvas` → сообщение о неподдерживаемом браузере.
12. Ширина 360 px на всех экранах → горизонтального скролла нет.
