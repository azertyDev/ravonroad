# 001 — План

## Решение

Три контейнера из SRS §1.1 (`db`, `api`, `edge`) поднимаются одним `docker-compose.yml`
с оверлеями лимитов по SRS §12.1 и §12.2. `api` получает три модуля: `config`
(валидация окружения), `prisma` (клиент + первая миграция с `CREATE EXTENSION postgis`)
и `health` (`/health`, `/ready` по SRS §10.1). `web` получает дерево маршрутов TanStack
Router с корнем `/$locale` (SRS §7.2), каркас i18n, дизайн-токены с локальными шрифтами
и базовый layout. Контракт статусов в `packages/shared-types` переименовывается в
`Report*` (преамбула SRS), туда же добавляется формат ошибки SRS §8.1.

Всё, что стоит процессорного времени или ходит наружу, в этом срезе отсутствует —
поэтому нагрузочный профиль SRS §1.6 на него не влияет. Единственное место, где он уже
учитывается, — конфигурация `edge` под будущий микрокэш (SRS §4.7) и лимиты памяти
SRS §12.

## Контракт (`packages/shared-types`)

По ADR-0006 контракт объявляется один раз и импортируется обеими сторонами.

- `REPORT_STATUSES` / `ReportStatus` — переименование существующих `REQUEST_*`
  (преамбула SRS). Значения не меняются: семь статусов глоссария.
- `ErrorCode` — union кодов SRS §8.1. В этом срезе список открывается кодами, нужными
  каркасу; каждый следующий срез его расширяет. Добавление кода без строки локали
  ломает `pnpm typecheck` — это и есть механизм полноты словарей (ADR-0006).
- `ApiErrorBody` — `{ error: { code, message, correlationId, details? } }`, `details`
  только для `VALIDATION_FAILED`.

Дублирование любого из этих типов в `apps/api` или `apps/web` — ошибка ревью
(`CLAUDE.md`).

## Схема БД

Появляется ровно одна миграция и ни одной таблицы: `CREATE EXTENSION IF NOT EXISTS
postgis;` (SRS §2, §2.14). Preview-флаг `postgresqlExtensions` не включается.

Таблицы приходят в 002 (SRS §2.2–§2.9, §2.13) и 004 (SRS §2.8, §2.10–§2.12, §2.15).
Причина такого порядка: `/ready` обязан проверять живую БД уже здесь (SRS §10.1),
а для этого достаточно соединения и `SELECT 1`.

Накат на непустую базу: базы ещё не существует, вопрос обратной совместимости
не стоит. Начиная с 002 каждая миграция обязана накатываться на копию дампа
(SRS §13).

## Эндпоинты

| Метод | Путь | Ответ | Раздел |
| --- | --- | --- | --- |
| `GET` | `/health` | `200 {"status":"ok","uptimeS":…}` всегда, пока процесс жив | SRS §10.1 |
| `GET` | `/ready` | `200` / `503 {"db":"down"}`, таймаут `SELECT 1` — 2 с | SRS §10.1 |

`/health/details` в этом срезе не появляется: он проверяет S3, Telegram и глубины
очередей, которых ещё нет (006).

Readiness проверяет только БД — включение S3 и Telegram выключало бы работающий сервис
из-за чужого сбоя (SRS §10.1).

## Telegram

Не затрагивается. Ни модуля, ни таблиц, ни webhook — 004. Переменные
`TELEGRAM_*` в `.env.example` остаются объявленными; комментарий рядом с
`TELEGRAM_MODERATOR_IDS` правится по ADR-0005 («источник первичного засева таблицы»,
а не «единственный механизм авторизации»).

## Frontend

**Маршруты** (SRS §7.1, §7.2):

```
/                        → редирект на /uz/
/$locale                 корень, валидация 'uz' | 'ru', иначе редирект на /uz/
/$locale/                заглушка главной: layout + счётчик-плейсхолдер (карта — 003)
```

Остальные маршруты (`reports`, `new`, `z/$token`) заводятся своими срезами: заготовок
каталогов «на будущее» не делаем (`CLAUDE.md`).

**Состояния экрана.** Layout, загрузка, ошибка и пустое состояние заводятся как
переиспользуемые компоненты сразу — SRS §13 требует их от каждой задачи, и заводить
их в каждом срезе заново дороже.

**TanStack Query** (SRS §7.5): провайдер с `refetchOnWindowFocus: false` глобально
(мобильный трафик платный, PRD §8.1). Ключи и `staleTime` конкретных запросов
приходят вместе с самими запросами в 002–003.

**Локаль** определяется из `navigator.languages`: первый элемент, начинающийся с `ru`,
даёт `/ru`, всё остальное — `/uz` (SRS §7.2). `Accept-Language` недоступен: сайт —
статический SPA без серверного рендера.

**Дизайн-токены.** Семь статусов получают цвет **и** форму — это требование PRD §8.2
(«статусы различаются не только цветом»). Соответствие статус → форма принято по
порядку перечисления дизайн-системы:

| Статус | Форма |
| --- | --- |
| `NEW` | кольцо |
| `ACCEPTED` | ромб |
| `IN_PROGRESS` | штриховка |
| `DONE` | галочка |
| `REJECTED` | крест |
| `DUPLICATE` | два квадрата |
| `OUT_OF_SCOPE` | косая черта |

Шрифты Noto Sans и IBM Plex Mono лежат локально в `apps/web/public/fonts` и
подключаются `@font-face` — внешних запросов за шрифтами нет ни одного. Разделитель
разрядов — U+00A0: тонкого пробела U+2009 в cmap IBM Plex Mono нет, и он отрисовался бы
заменой глифа.

## Инфраструктура

**`docker-compose.yml`** — три сервиса SRS §1.1. Лимиты памяти выносятся в оверлеи:
прод по SRS §12.1 (`db` 640 МБ, `api` 576 МБ, `edge` 96 МБ), dev по SRS §12.2
(320/288/64 МБ). Одна и та же composition поднимается в обеих средах (`CLAUDE.md`).

**`edge`** (SRS §1.1, §7.2, §9.8): статика `web`, reverse proxy на `api:3000`,
SPA-fallback на `index.html` (иначе прямая ссылка `/ru/z/<token>` даст 404 от статики),
заголовки безопасности, gzip/brotli. Секция `proxy_cache` объявляется здесь пустой
и наполняется в 003 (SRS §4.7) — иначе кэшировать нечего.

**Образы** (SRS §12.2 п.1): собираются в GitHub Actions и публикуются в GHCR,
на серверах только `docker pull`. `docker build` на e2-micro упирается в память
и в 0,25 vCPU baseline.

**Миграции** — одноразовый контейнер `docker compose run --rm migrate`
(SRS §12.2 п.2), постоянного контейнера под них нет.

**Логи** — драйвер `json-file` с `max-size=10m`, `max-file=3` (SRS §8.4, §12.2 п.5).

## Риски

| Риск | Что делаем |
| --- | --- |
| Vitest не согласован — половина «Готово когда» непроверяема | T-003 вынесена отдельной задачей и помечена как требующая решения; до её закрытия остальные задачи проверяются вручную по AC |
| Значений дизайн-токенов нет в репозитории | T-014 блокируется до получения артефакта; набор форм статусов от палитры не зависит и делается сразу |
| CSP ломает Яндекс JS API (SRS §16 п.14) | В 001 CSP пишется по SRS §9.8, в 003 уточняется по фактическим запросам в консоли; правка — одна строка nginx |
| Prisma 7 + `Unsupported` даёт дрейф схемы | В этом срезе `Unsupported` не появляется вовсе: первая колонка `geography` приходит в 002 вместе с `district` (ADR-0003) |
| **VPS 2 ГБ / GCE 1 ГБ** | Лимиты контейнеров прописаны с первого коммита (SRS §12.1, §12.2); свободных 380 МБ на проде и 80 МБ на dev — не запас, а расчёт. Появление четвёртого постоянного контейнера требует пересмотра SRS §12 |
| Архитектура VPS неизвестна (SRS §16 п.7) | Dockerfile собирается под `linux/amd64` по умолчанию; при подтверждении arm64 добавляется вторая платформа в матрицу сборки |

Нагрузочный профиль SRS §1.6 в этом срезе не воспроизводится и не проверяется:
принимать нечего.

## Проверка

1. `docker compose up` на чистой машине → три контейнера в `running`,
   `curl -f localhost/api/health` → `200`.
2. `docker compose stop db` → `curl -s -o /dev/null -w '%{http_code}' localhost/api/ready`
   → `503`; `/health` → `200`.
3. `curl -I localhost/uz/z/whatever` → `200 text/html` (SPA-fallback).
4. `curl -I localhost/` → присутствуют `Referrer-Policy: no-referrer`,
   `X-Content-Type-Options: nosniff`, `Content-Security-Policy`.
5. Открыть `/` в браузере → редирект на `/uz/`; переключить язык на странице с
   search-параметрами → параметры на месте, `<html lang>` изменился.
6. Сузить окно до 360 px → горизонтального скролла нет.
7. Пройти шапку и переключатель языка с клавиатуры → фокус виден на каждом шаге.
8. `pnpm lint && pnpm typecheck && pnpm test` → зелено.
9. `grep -r 'REQUEST_STATUSES' .` → ноль совпадений вне `pnpm-lock.yaml`.
10. Открыть вкладку «Сеть», отфильтровать по стороннему домену → запросов за шрифтами
    нет.
11. Пуш ветки → CI зелёный; мерж в `dev` → образ появился в GHCR и запускается
    `docker run`.
