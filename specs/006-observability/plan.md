# 006 — План

## Решение

Наблюдаемость строится на том, что уже есть, и не приносит ни одного нового
контейнера. Correlation id живёт в `AsyncLocalStorage` (`node:async_hooks`) — сквозной
прокид через параметры не нужен, дополнительная зависимость тоже (SRS §8.3). Логи —
JSON в stdout, один объект на строку, забирает `docker logs` с ограничением драйвера
(SRS §8.4). Метрики — SQL-запросы в `docs/metrics.sql`, потому что данные и есть
метрики (SRS §10.3). Алерты доставляет тот же бот в приватный чат координатора:
канал уже есть и уже оплачен (SRS §10.4).

Prometheus и Grafana не разворачиваются: ~250 МБ памяти при бюджете SRS §12 —
цена несоразмерная.

Три числа глубины очередей считаются воркерами при каждом проходе и пишутся событием
`queue_depth`. Без них перегрузка обнаруживается по сообщению в группе «а где мои
фотки» — то есть после того, как её заметил житель.

## Затрагиваемые модули

| Модуль | Что появляется |
| --- | --- |
| `apps/api/src/common` | `AsyncLocalStorage` для correlation id, JSON-логгер |
| `apps/api/src/health` | `/health/details` |
| `apps/api/src/media`, `src/telegram` | Событие `queue_depth` в проходах воркеров |
| `apps/api/src/telegram` | Алерты, активная проверка `getWebhookInfo` |
| `apps/api/src/maintenance` | Суточная задача очистки |
| `docker/backup` | `pg_dump` в S3 |
| `docs/metrics.sql`, `scripts/seed-load.ts` | Метрики и нагрузочный сид |

## Контракт

Изменений в `packages/shared-types` нет: `correlationId` уже входит в `ApiErrorBody`
с 001 (SRS §8.1). Здесь он начинает заполняться реальным значением из
`AsyncLocalStorage` вместо генерации на месте.

Форма `/health/details` — внутренняя, потребителя вне репозитория у неё нет, поэтому
в общий пакет она не выносится.

## Схема БД

Новых таблиц нет. Суточная задача работает с существующими:

| Действие | Таблица | Срок | Раздел |
| --- | --- | --- | --- |
| `UPDATE ... SET created_ip = NULL` | `report` | 30 дней с создания | SRS §9.8 |
| `UPDATE ... SET contact_* = NULL, contacts_deleted_at = now()` | `report` | 90 дней после терминального статуса | PRD §9.2.5 |
| `DELETE` | `processed_update` | 7 дней | SRS §2.11 |
| `DELETE` | `bot_prompt` | по `expires_at` | SRS §2.12 |

Обе чистки `report` — один проход, один `UPDATE` на условие. CHECK из SRS §2.2
не даст сохранить `contacts_deleted_at` вместе с непустыми контактами, поэтому
рассогласование невозможно by construction.

Индексов срез не добавляет: чистки идут раз в сутки и полный проход по десяткам
тысяч строк дешевле поддержки лишнего индекса.

## Эндпоинты

| Метод | Путь | Ответ | Раздел |
| --- | --- | --- | --- |
| `GET` | `/health/details` | Сводка по БД, S3, Telegram, глубине outbox и возрасту последнего апдейта | SRS §10.1 |

`/health` и `/ready` из 001 не меняются. Readiness намеренно проверяет **только** БД:
сайт обязан работать при недоступном Telegram (PRD §8.6) и продолжает отдавать карту
при недоступном S3.

`/health/details` не содержит секретов и персональных данных, поэтому доступен без
авторизации — заводить единственный в системе секрет ради страницы диагностики
несоразмерно (SRS §10.1). Проверки S3 и Telegram кэшируются на 60 секунд, иначе
страница диагностики сама станет нагрузкой на внешние сервисы.

## Telegram

Бот получает вторую роль — канал доставки алертов (SRS §10.4):

- сообщения уходят в `TELEGRAM_ALERT_CHAT_ID`, а не в группу волонтёров;
- дедупликация: не чаще одного сообщения на условие в час;
- восемь условий алерта — из SRS §10.4, без добавлений и без сокращений;
- активная проверка `getWebhookInfo` каждые 5 минут: тишина в webhook неотличима
  от отсутствия событий, поэтому пассивное наблюдение здесь не работает.

Слабое место названо явно и принимается: если недоступен сам Telegram, алерт о его
недоступности не дойдёт. Второй канал — внешний uptime-пинг на `/health`
(см. «Требует решения»).

Алерты идут **мимо** `telegram_outbox`: бюджет 20 сообщений/мин предназначен группе,
и сообщение о переполненной очереди не должно вставать в ту же очередь, о которой
сообщает.

## Frontend

Срез не добавляет ни маршрутов, ни компонентов. Единственное касание `web`:
`correlationId` показывается на экране ошибки, чтобы житель мог его назвать
(SRS §8.3). Компонент ошибки существует с 001 — здесь в него добавляется строка.

## Риски

| Риск | Что делаем |
| --- | --- |
| ⚡ **Всплеск обнаруживается по жалобам** (SRS §1.6) | Три глубины очередей пишутся при каждом проходе воркеров; алерты по порогам SRS §10.4 приходят за 10 минут до того, как это заметит житель |
| ⚡ Очередь модерации — метрика про людей | При 1000 заявок в час она растёт быстрее всех остальных и раньше всех упирается в потолок; алерт при > 200 — сигнал включать пакетные действия (SRS §12.3 п.2) |
| Алерт о недоступном Telegram не доходит | Известное слабое место; второй канал — внешний uptime-пинг на `/health` |
| Логи заполняют диск e2e-micro | Драйвер `json-file` с `max-size=10m`, `max-file=3` — максимум 30 МБ на контейнер (SRS §8.4, §12.2 п.5) |
| Токен или телефон попадают в лог | Запретный список SRS §8.4 закрыт тестом на форму строки лога, а не чек-листом ревью |
| `pg_dump` съедает память под всплеском | Запускается разовым контейнером в тихие часы; на dev не запускается вовсе — восстанавливать нечего (SRS §12.2 п.4) |
| Проверка восстановления не выполняется | Ответственный и периодичность вынесены в «Требует решения»; без назначенного человека процедура не работает |
| Алерты превращаются в шум | Дедупликация раз в час на условие; восемь условий и ни одного «на всякий случай» |
| **VPS 2 ГБ / GCE 1 ГБ** | Ноль новых постоянных контейнеров: логи в stdout, метрики — файл SQL, алерты — тот же бот. `pg_dump` — разовый контейнер, попадает в свободные ~380 МБ прода (SRS §12.1) |

## Проверка

1. Вызвать ошибочный запрос → идентификатор из тела ошибки находится в логе
   `docker logs api | grep <id>`, и в выдаче все события этого запроса.
2. Прислать свой `X-Request-Id` → он вернулся в заголовке и стоит в теле ошибки.
3. `docker logs api | grep -E '<токен>|<телефон>'` после прохода полного сценария →
   пусто; тест на запретный список зелёный.
4. Пройти по списку SRS §10.2 → все 12 событий встречаются в логе после прогона
   сценариев.
5. `curl localhost/api/health/details` → сводка по БД, S3, Telegram, глубине outbox
   и возрасту апдейта; секретов нет.
6. Остановить S3-заглушку → `/health/details` показывает деградацию, `/ready`
   по-прежнему `200`.
7. Остановить photo-воркер и создать 250 заявок → `queue_depth` растёт, через 10 минут
   в тестовом чате алерт; повторные проверки в течение часа второго сообщения не дают.
8. Сбросить webhook чужим `setWebhook` → в пределах 5 минут приходит алерт.
9. Подменить время на +31 день → `created_ip` обнулён; на +91 день после терминального
   статуса → контакты удалены, заявка и фото на месте.
10. Дождаться суточной задачи → в S3 под префиксом бэкапов лежит сжатый дамп; после
    15 запусков копий 14, не больше.
11. Развернуть последний дамп на dev-машине → база поднимается, приложение работает.
12. Прогнать `docs/metrics.sql` → P-4 возвращает 0 строк, остальные метрики считаются;
    результат сверен с PRD §1.3.
13. Засеять 5000 заявок, прогнать Lighthouse и замеры → p95 по PRD §8.1 записаны;
    отклонения зафиксированы явно.
