# Контракт API — `packages/shared-types`; OpenAPI и генераторы клиента не создаются

## Контекст и постановка задачи

Фронтенд и бэкенд лежат в одном pnpm-workspace, пишутся на одном TypeScript, собираются
одной командой и деплоятся одним релизом. Потребитель API ровно один — `apps/web`.
Внешних интеграторов нет и не планируется: реестр `OUT_OF_SCOPE` в v2 отдаётся файлом
GeoJSON/CSV, а не программным интерфейсом (BRD §7).

Нужно, чтобы типы запросов и ответов не разъезжались между сторонами. Классический ответ —
OpenAPI-спецификация плюс генератор клиента. Оправдан ли он здесь?

## Рассмотренные варианты

* Общий пакет типов `packages/shared-types`, импорт обеими сторонами
* OpenAPI как источник истины, генерация типов и клиента из спеки
* Декораторы `@nestjs/swagger`, спека генерируется из кода, клиент — из спеки
* Дублировать типы на обеих сторонах вручную

## Решение

Выбран **общий пакет `packages/shared-types`**: типы запросов, ответов, коды ошибок
и union-ы доменных значений объявляются один раз и импортируются `apps/api`
и `apps/web` напрямую. OpenAPI не создаётся, генераторы клиента не подключаются.

Цепочка «код → спека → генератор → код» здесь заменяется одним шагом «код → код»,
и `tsc` проверяет её на каждом `pnpm typecheck`. Спека была бы посредником между двумя
пакетами одного репозитория, которые и так собираются вместе.

Что обязано жить в пакете: тело и ответ каждого эндпоинта, `ReportStatus` и остальные
доменные union-ы, полный список кодов ошибок (`ErrorCode`), формы результатов двух
`$queryRaw` из SRS §2.14. Дублирование любого из этих типов на стороне — ошибка ревью
(`CLAUDE.md`).

### Последствия

* Хорошо: расхождение контракта невозможно молча — оно ломает `pnpm typecheck`, то есть
  CI, а не проявляется в рантайме.
* Хорошо: ноль генераторов, ноль шага сборки, ноль зависимостей. Правка типа — одна
  правка в одном файле.
* Хорошо: `ErrorCode` как union заставляет клиента иметь строку локали на каждый код:
  добавили код без перевода — не собралось (SRS §8.1).
* Хорошо: рефакторинг с переименованием проходит по обеим сторонам одним движением IDE.
* Плохо: типы не проверяют рантайм. Валидация входа на сервере пишется отдельно и
  вручную — типы не заменяют её ни в одном месте, где данные приходят снаружи.
* Плохо: машинописной документации API не существует. Замена — §4 SRS, который надо
  править руками в том же изменении, что и код.
* Плохо: появление внешнего потребителя API потребует пересмотра этого ADR. Признак
  для пересмотра сформулирован ниже.

## Подтверждение

В `apps/api` и `apps/web` нет ни одного объявления типа запроса или ответа — только
импорты из `@ravonroad/shared-types`. В репозитории нет `.yaml`/`.json` спеки OpenAPI
и нет зависимостей-генераторов.

Признак для пересмотра: появляется потребитель API вне этого репозитория. Тогда
спецификация становится границей команд, а не посредником внутри одного workspace,
и цена её ведения оправдана.

## Плюсы и минусы вариантов

### Общий пакет типов

* Хорошо: одна декларация, проверка компилятором, нулевая инфраструктура.
* Плохо: работает только внутри одного репозитория и одного языка.

### OpenAPI как источник истины

* Хорошо: язык-независимый контракт, готовая документация, mock-серверы.
* Плохо: третий артефакт между двумя пакетами, которые собираются вместе; ошибиться
  можно и в спеке.
* Плохо: генератор — зависимость, версия, шаг сборки и слой сгенерированного кода
  в diff-ах.

### `@nestjs/swagger` из кода

* Хорошо: спека не расходится с реализацией, документация «бесплатна».
* Плохо: декораторы на каждом DTO — заметный объём разметки ради документа, который
  сейчас некому читать.
* Плохо: клиент всё равно генерируется отдельным инструментом, то есть шаг сборки
  никуда не девается.

### Ручное дублирование

* Хорошо: ноль инфраструктуры.
* Плохо: расхождение — вопрос времени, и обнаруживается оно в проде.

## Дополнительная информация

Правило зафиксировано в `CLAUDE.md` › «Чего в системе нет» и › «Правила кода».
Контракт эндпоинтов — `docs/srs.md` §4, формат ошибки — §8.1.

При реализации первого среза `packages/shared-types/src/index.ts` переименовывает
`REQUEST_STATUSES` / `RequestStatus` в `REPORT_STATUSES` / `ReportStatus`: сущность
называется `Report`, а `Request` в NestJS занят HTTP-запросом (см. преамбулу `docs/srs.md`).
