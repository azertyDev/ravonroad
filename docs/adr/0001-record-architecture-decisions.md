# Фиксировать архитектурные решения в виде ADR

## Контекст и постановка задачи

Проект ведут несколько человек и несколько AI-агентов, работающих в разных сессиях без общей
памяти. Решения вроде «почему нет авторизации», «почему контракт живёт в `packages/shared-types`,
а не в OpenAPI», «почему геокодер Яндекса не используется» невозможно восстановить из кода —
код показывает результат, но не альтернативы и не причину отказа от них. Без записи каждая
новая сессия переоткрывает уже закрытый вопрос.

Как сохранять контекст архитектурных решений так, чтобы он переживал смену исполнителя?

## Рассмотренные варианты

* ADR-файлы в репозитории (формат MADR)
* Раздел «Решения» внутри `docs/srs.md`
* Комментарии в коде рядом с местом реализации
* Внешний трекер / вики

## Решение

Выбран вариант **ADR-файлы в репозитории в формате MADR**, потому что решения версионируются
вместе с кодом, ревьюятся тем же процессом, что и код, и доступны агенту без внешних доступов.

### Последствия

* Хорошо: решение и его причина живут в одном коммите с изменением, которое его реализует.
* Хорошо: отказ от варианта зафиксирован явно — повторное обсуждение начинается не с нуля.
* Плохо: требуется дисциплина — ADR, написанный «потом», обычно не пишется никогда.

## Подтверждение

Существующие ADR лежат в `docs/adr/`. Изменение, которое меняет архитектуру
(схема БД, границы модулей, внешняя зависимость, протокол интеграции), не проходит ревью
без ADR в том же MR.

## Плюсы и минусы вариантов

### ADR-файлы в репозитории (формат MADR)

* Хорошо: версионируются вместе с кодом, видны в diff.
* Хорошо: MADR — устоявшийся формат, не требует своего описания.
* Плохо: файлов со временем много, нужен индекс.

### Раздел «Решения» внутри `docs/srs.md`

* Хорошо: одно место, ничего не нужно искать.
* Плохо: SRS описывает текущее состояние, а ADR — историю; они конфликтуют при правках.
* Плохо: отменённое решение приходится удалять, вместе с ним исчезает причина.

### Комментарии в коде

* Хорошо: максимально близко к месту реализации.
* Плохо: решение об отказе от варианта негде записать — соответствующего кода не существует.

### Внешний трекер / вики

* Хорошо: удобно читать не-разработчикам.
* Плохо: агент без сетевого доступа к трекеру не увидит контекст.
* Плохо: расходится с кодом, потому что живёт вне ревью.

## Дополнительная информация

Формат: MADR 4.0.0 (https://adr.github.io/madr/). Нумерация — сквозная, четыре цифры,
файл `docs/adr/NNNN-kebab-case-заголовок-на-английском.md`. Этот файл одновременно является
шаблоном: копируем его, меняем frontmatter и содержимое. Статусы: `proposed`, `accepted`,
`rejected`, `deprecated`, `superseded by ADR-NNNN`.
