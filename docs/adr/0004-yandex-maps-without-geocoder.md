# Яндекс Карты только как виджет и тайлы; геокодер не используется, адрес не хранится

## Контекст и постановка задачи

Житель ставит пин на карте, бригада едет по координатам. Соблазн очевиден: вызвать
геокодер и получить текстовый адрес — «удобнее читать в карточке», «понятнее в отчёте
спонсору».

Лицензия Яндекс Карт для бесплатного использования ограничивает хранение результатов
геокодирования сроком порядка 30 дней. Заявки же живут всё время кампании — три года
и дольше, а фотоархив «до/после» является её основным активом. Хранение адреса дольше
разрешённого срока делает нелегальным весь архив, а не отдельное поле.

Отдельно: срез по 12 районам (BR-012) — обязательное требование, и оно тоже выглядит
как задача для геокодера.

## Рассмотренные варианты

* Яндекс JS API: только виджет выбора точки и тайлы; район считаем сами по PostGIS
* Яндекс JS API + геокодер, адрес хранится
* Яндекс JS API + геокодер, адрес не хранится, запрашивается на лету при показе
* Другой поставщик карт (OSM/MapLibre + Nominatim)

## Решение

Выбран вариант **«только виджет и тайлы»**: адрес не запрашивается и не хранится вообще,
источник координат — исключительно Geolocation API браузера и положение пина, район
вычисляется point-in-polygon по `data/geo/tashkent-districts.geojson` на сервере.

Место человеческими словами описывает поле «ориентир», которое заполняет сам житель
(US-009) — оно не является геокодированным адресом и лицензией не ограничено.

### Последствия

* Хорошо: 30-дневное ограничение просто не применяется — хранить нечего.
* Хорошо: район всегда определён и всегда одинаково (P-5 требует 100%), не зависит
  от доступности внешнего сервиса и от его квот.
* Хорошо: минус один внешний вызов на создание заявки и минус один источник отказа.
* Хорошо: границы районов — официальные данные хокимията, а не чужая интерпретация;
  эксклав Мирзо-Улугбекского учтён (`data/geo/README.md`).
* Плохо: в карточке Telegram нет строки «ул. такая-то, дом такой-то» — есть координаты,
  ссылка на точку и ориентир от жителя. Для навигации этого достаточно, для отчёта
  спонсору — район плюс координаты.
* Плохо: качество «ориентира» зависит от жителя и может быть плохим. Компенсируется
  фотографией и точным пином.
* Плохо: сохраняется зависимость от Яндекса как поставщика тайлов и JS-виджета.
  [требует проверки: условия использования тайлов и JS API v3 для некоммерческой
  волонтёрской кампании, необходимость ключа и его лимиты]

## Подтверждение

В коде нет ни одного обращения к `geocode`, `suggest` и любому HTTP-эндпоинту Яндекса,
кроме загрузки JS API и тайлов. В схеме БД нет колонки с адресом. Появление такой
колонки или такого вызова — нарушение этого ADR и повод остановить ревью.

## Плюсы и минусы вариантов

### Только виджет и тайлы

* Хорошо: лицензионный риск снят целиком, а не смягчён.
* Хорошо: район считается детерминированно и офлайн.
* Плохо: текстового адреса нет нигде.

### Геокодер, адрес хранится

* Хорошо: читаемый адрес в карточке и в отчёте.
* Плохо: прямое нарушение срока хранения — под удар попадает весь архив кампании.
* Плохо: квоты и тарификация становятся зависимостью процесса подачи заявки.

### Геокодер на лету, без хранения

* Хорошо: формально хранения нет.
* Плохо: адрес нужен в карточке Telegram, а сообщение в Telegram — это и есть хранение,
  которым мы не управляем и не можем удалить по истечении срока.
* Плохо: запрос на каждый показ — нагрузка и квоты растут с посещаемостью.

### OSM/MapLibre + Nominatim

* Хорошо: свободная лицензия, нет 30-дневного ограничения.
* Плохо: границы районов в OSM расходятся с официальными — эксклав Мирзо-Улугбекского
  приписан Яшнабадскому, расхождение по площади ~2000 га (`data/geo/README.md`);
  именно поэтому OSM уже отклонён как источник границ.
* Плохо: смена поставщика карт — отдельное решение со своей стоимостью, и оно не
  требуется для того, чтобы отказаться от геокодера.
