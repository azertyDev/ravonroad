# Модульный монолит; Telegram-бот — модуль внутри `apps/api`

## Контекст и постановка задачи

Система состоит из двух каналов: публичный сайт для жителей и Telegram-группа для бригады.
Оба работают с одними и теми же заявками, одной схемой БД и одними инвариантами
(«`DONE` не существует без фото „после“»). Бот не просто отправляет уведомления — он
меняет состояние заявок.

Прод — VPS на 2 ГБ, dev — GCE e2-micro на 1 ГБ (`CLAUDE.md`). Память — жёсткое ограничение.

Как разместить бот относительно API, чтобы инварианты не разъезжались, а бюджет памяти
не был съеден процессами?

## Рассмотренные варианты

* Один NestJS-сервис, бот — модуль внутри него
* Отдельный сервис бота с собственным процессом и общей БД
* Отдельный сервис бота, общающийся с API по HTTP
* Serverless-функция под webhook

## Решение

Выбран **один NestJS-сервис, модульный монолит; Telegram-бот — модуль
`apps/api/src/telegram/`**, потому что бот меняет те же агрегаты, что и API, и вынос его
за границу процесса создал бы вторую точку, где нужно повторить проверки статусов,
allowlist и инварианта фото — не купив ничего взамен.

Следствия для устройства модуля: webhook — обычный контроллер Nest, повторная доставка
и отложенная отправка обслуживаются таблицей `telegram_outbox` и `setInterval` в том же
процессе. Ни брокера, ни отдельного воркера в системе нет.

### Последствия

* Хорошо: транзакция «сменить статус + записать историю + поставить правку карточки
  в очередь» — одна транзакция БД, а не распределённая сага.
* Хорошо: один контейнер вместо двух — по бюджету §12 SRS это ~250 МБ разницы,
  то есть на dev-машине выбор между «два процесса» и «работает».
* Хорошо: типы контракта и доменные правила существуют в одном экземпляре.
* Плохо: тяжёлая обработка фото и обслуживание HTTP делят один event loop. Закрыто
  семафором на 2 конвейера sharp (SRS §5.6), а не архитектурой.
* Плохо: деплой атомарен — перезапуск ради правки текста карточки роняет и сайт.
  Приемлемо: рестарт занимает секунды, SLA у волонтёрской кампании нет.
* Плохо: горизонтальное масштабирование закрыто — лимиты и буфер альбомов живут
  в памяти процесса. Записано явно в SRS §12.3, чтобы второй экземпляр не подняли
  по неосторожности.

## Подтверждение

В `apps/api` один `main.ts` и один контейнер `api` в `docker-compose`. Появление второго
long-running процесса или контейнера с кодом приложения — повод для нового ADR,
отменяющего этот.

## Плюсы и минусы вариантов

### Один сервис, бот — модуль

* Хорошо: общие инварианты и транзакции без распределённых протоколов.
* Хорошо: минимальный расход памяти.
* Плохо: общий event loop, общий деплой.

### Отдельный сервис с общей БД

* Хорошо: изоляция отказов, независимый деплой.
* Плохо: две кодовые базы применяют одни и те же правила к одним таблицам — расхождение
  вопрос времени.
* Плохо: +1 контейнер Node (~250 МБ) при бюджете 1 ГБ на dev.

### Отдельный сервис, общение по HTTP

* Хорошо: чистая граница.
* Плохо: внутренний API нужно спроектировать, версионировать и защитить — работа
  соразмерна самому боту.
* Плохо: та же плата за память плюс сетевые отказы там, где был вызов функции.

### Serverless под webhook

* Хорошо: ноль памяти в простое.
* Плохо: прод — свой VPS; вводить второго провайдера ради одного эндпоинта
  несоразмерно.
* Плохо: холодный старт и пул соединений к Postgres на 20 подключений.
